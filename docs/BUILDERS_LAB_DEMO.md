# Builders' Lab demo runbook

This runbook prepares Unfold for a reliable end-to-end demo without storing credentials or fabricated frontend results in the repository.

## Local setup

Prerequisites: Python 3.12+, Node.js 22, and either PostgreSQL or the development SQLite fallback.

```powershell
python -m pip install -r backend/requirements.txt
npm --prefix frontend ci
python backend/manage.py migrate
python backend/manage.py loaddata experiments
python backend/manage.py seed_hypothesis_engine
$env:UNFOLD_DEMO_EMAIL = "demo@unfold.local"
$env:UNFOLD_DEMO_PASSWORD = "choose-a-private-demo-password"
python backend/manage.py seed_demo
```

Run the two development servers in separate terminals:

```powershell
python backend/manage.py runserver
npm --prefix frontend run dev
```

Open `http://localhost:5173`. The Vite proxy sends `/api` requests to Django at `http://127.0.0.1:8000`.

## Demo account strategy

- Email comes from `UNFOLD_DEMO_EMAIL` and defaults to `demo@unfold.local`.
- Password must come from `UNFOLD_DEMO_PASSWORD`; there is no repository default.
- `seed_demo` is atomic and repeatable. It resets data belonging only to that demo user.
- The demo user is always non-staff and non-superuser.
- Optional admin creation requires both `UNFOLD_ADMIN_EMAIL` and `UNFOLD_ADMIN_PASSWORD` when `seed_hypothesis_engine` runs.

Do not place the real demo password in source, screenshots, notes committed to Git, or public demo instructions.

## Recommended demo route

1. Start on the landing page and explain that Unfold replaces a fixed purpose quiz with short real-world trials.
2. Log in using the environment-configured demo account. The session persists across a refresh.
3. On Home, open the active **Teach Someone Something** experiment. Four of five check-ins are already complete.
4. Complete day 5 live. Point out that the saved screen reflects the answers just entered.
5. Complete the final reflection and open the generated report. Explain fit signal and evidence confidence as summaries, not grades.
6. Open **Evidence Vault** to compare the completed photography, writing, coding, and teaching evidence.
7. Open **Insights** and use the “How Unfold learns” sequence: try → reflect → evidence → patterns → hypothesis → test again.
8. Open **What I've learned**. Show uncertain, emerging, and supported states, then inspect the source evidence for a hypothesis.
9. Choose **Test this assumption**. Explain that the recommended nature experiment keeps a supported trait while changing its context.
10. Open Profile to show activity history, then log out and refresh to confirm the protected app returns to login.

The exact recommendation is calculated from untried experiments and can change if the demo dataset changes; describe the reason shown by the UI rather than memorizing a title.

## Render production configuration

The repository's `render.yaml` creates one Django/React web service, PostgreSQL, and an hourly reminder job. The web build compiles Vite, installs Python dependencies, collects static files, runs migrations, loads starter experiments, and seeds the deterministic hypothesis definitions.

Required web environment variables:

- `DATABASE_URL` — supplied by the Render database.
- `SECRET_KEY` — generated by Render; production now fails fast if it is absent.
- `DEBUG=False`.
- `ALLOWED_HOSTS=.onrender.com` (add a custom domain if used).
- `SITE_URL=https://<actual-public-host>` — no trailing slash.
- `UNFOLD_DEMO_EMAIL` and `UNFOLD_DEMO_PASSWORD` — used only when an operator runs `seed_demo`.

Email features require:

- `RESEND_API_KEY`.
- `DEFAULT_FROM_EMAIL` using a sender/domain verified in Resend.
- The same `SITE_URL`, `RESEND_API_KEY`, and `DEFAULT_FROM_EMAIL` on the reminder cron job.

Optional variables:

- `SENTRY_DSN`.
- `CSRF_TRUSTED_ORIGINS` for additional HTTPS origins. The current Render hostname is added automatically.
- `CORS_ALLOWED_ORIGINS` only when a separately hosted frontend calls the API.
- `SECURE_HSTS_SECONDS` to override the production default.

After the first successful deploy, open a Render shell and run:

```bash
python backend/manage.py seed_demo
```

The Render environment supplies the demo credentials. Never put them in the command itself. Confirm `/api/v1/health/` returns `{"status":"ok","database":"ok"}`.

## Emergency local fallback

If the hosted service is unavailable, use the local setup above and present from `http://localhost:5173`. Run `seed_demo` again immediately before the session to restore the intended story. Keep both server terminals visible until the browser has loaded Home and the health endpoint is green.

If email delivery is unavailable, do not demonstrate password reset or reminders. The core experiment flow does not depend on the email provider.
